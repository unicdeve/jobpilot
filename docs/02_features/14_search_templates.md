# Feature: Search Templates

## Status

Implemented.

## Purpose

Give the user a set of search criteria that are known to work, so that their first search is a good one rather than a guess.

A saved search is the only thing that drives discovery, and writing a good one requires knowing how `SearchCriteria.Matches` behaves.
That behaviour is not visible from the form, and it is unforgiving: every word must appear, words are matched as substrings, and `Keywords` is matched against the whole job description rather than the title.
A reasonable-looking search can therefore return almost nothing, or almost everything, and nothing on screen distinguishes the two.

## What a template is

A named set of criteria, in a group of related ones.

Importing a template creates an ordinary saved search.
Nothing links the two afterwards: the copy belongs to the user, to rename, narrow or delete, and a later release that corrects a template never rewrites a search they have already adopted.

A group is a menu, not a bundle.
`SearchCriteria` cannot express "or", so a job titled Engineer at one board and Developer at another needs two searches.
Both are offered, and adopting only one silently discards half the market.

## Where the catalog lives

Static Go data in `internal/core/domain`, served by the daemon at `GET /v1/search-templates`.

The desktop application and the CLI both read it from there, so the two cannot offer different criteria under the same name, and correcting a template is a release rather than a migration.
The catalog is never generated by the LLM: these are criteria whose behaviour has been measured, and a model inventing new ones at runtime would return to exactly the guesswork templates exist to remove.

## How the catalog was built

Every candidate criterion was measured against 654 live postings fetched from all five sources at once.
Three rules came out of it, and they govern what may be added.

### Put the distinguishing word in Title, not the role word

"Backend" in a title is what makes a job a backend job.
"Engineer" only decides which half of the market is visible, because a board writes either Engineer or Developer and `Matches` requires every term.

Measured: `title="backend engineer"` and `title="backend"` returned the same 11 postings, so pinning the role word bought nothing and would have cost every posting titled Developer.
The user's own "React Engineer" search, which set `title="developer"`, returned 5 postings out of 654 — "engineer" appears in 173 titles and "developer" in 20.

### Split a compound word rather than guessing a spelling

Terms are matched as substrings, so each half of a split word occurs inside every spelling of it, while no single spelling occurs inside the others.

Measured, as a title term: `"full stack"` found 26 postings, `"full-stack"` 15, `"fullstack"` 9.
The same applies to `"back end"` and `"front end"`, which each found one more posting than the closed-up spelling.

### Never search descriptions for a short or common word

`Keywords` is matched against the whole description, where ordinary prose supplies almost anything.

Measured: `keywords="go"` matched 426 of 654 postings — on "go-to", "goals", "google" and "Django".
`keywords="rust"` matched 151, on "trust".
`keywords="full stack"` matched 135, mostly descriptions of Sales Engineer and Product Operations roles that happen to use both words.

Substring matching costs the abbreviations too.
As a title term, "ui" matches "Cruise" and "Recruiter", "ux" matches "Luxury", and "ml" matches the German "Teamleiter".
No template searches for UI, UX, ML, SRE, iOS or Go by those names; each is spelled out, or replaced by a longer word that means the same thing.
"Site Reliability" and "Machine Learning" are the spelled-out cases; "UX Designer" searches descriptions for "usability" instead.

## What the stack templates cost

The templates in "Engineering by stack" search the description, because boards almost never put a stack in the title — measured, "typescript" appeared in no title at all and "golang" in three.

A description mentions a technology for many reasons, and a sales role at an infrastructure company lists the whole stack.
`Matches` cannot tell "this job is Go" from "this page says Go", and no wording of the criteria makes it able to.
The group says so, and `TestAStackTemplateAlsoMatchesAPassingMention` pins it, so that it stays a known price rather than becoming a surprise.

## What this is worth

Measured against the same 654 postings, for the profile that prompted the feature:

| | postings found |
| --- | --- |
| their three specialist searches (Fullstack, Frontend, React) | 26 |
| the equivalent templates | 112 |

Their fourth search, keywords and title both "engineer", found 199 — but 65 of those have no software word in the title at all: Sales Engineer, Solutions Engineer, Engineering Manager, Embedded Robotics Engineer.
Breadth of that kind is not the same as finding more of the right jobs, and it is paid for later, one model call at a time, when each one is scored.

## Acceptance Criteria

### AC-001
The same catalog is served to the desktop application and the CLI, from one place.

### AC-002
Importing a template creates an ordinary saved search, editable and deletable like any other.

### AC-003
A template already adopted can be adopted again; the second copy is numbered rather than refused, and the first is not overwritten.

### AC-004
An unknown template ID writes nothing.

### AC-005
Every template in the catalog matches at least one real posting, and no template matches a posting of a kind it does not offer.

### AC-006
No template searches descriptions for a word short enough that ordinary prose supplies it.

## Deferred

**Suggesting templates from the candidate's profile.**
The profile already holds skills and job titles, so the group a user needs could be chosen for them rather than browsed.
It is deferred because the catalog is small enough to read, and because a wrong suggestion at that moment is worse than none: onboarding is where a user has least context to judge it.

**Templates that set a location or a salary floor.**
Every template here sets only title and keywords.
A location belongs to the user, not to the kind of work, and a salary floor set by the product would be a claim about what a role is worth.
The same holds for where the candidate works from (ADR-0023 §4): no template sets it, and adopting one gives each search the profile's country, which the user can change.
